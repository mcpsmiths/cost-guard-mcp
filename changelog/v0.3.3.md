# v0.3.3 — 2026-10-10

A patch release: one real Snowflake auth fix, a security-driven rebuild of the Docker base
image and two transitive dependency bumps, a behaviour-preserving restructure of how the
tools are declared, and a dependency refresh - every change verified by the unit suite and
by the live BigQuery/Snowflake integration workflow on the release commit.

### Fixed

- **Snowflake: an empty `SNOWFLAKE_PRIVATE_KEY_PASSPHRASE` is treated as no passphrase.**
  GitHub Actions (and other secret stores) set a variable referencing a missing secret to
  `""`, not unset; the connector then failed with "Password was given but private key is
  not encrypted." for an unencrypted key. Confirmed live in `integration.yml` before the
  fix (#63).
- **Docker base image re-pinned** to the rebuilt upstream digest of
  `ghcr.io/astral-sh/uv:python3.12-trixie-slim` (Debian 13.7). The previous digest carried
  four HIGH OS CVEs - `libpcre2-8-0` CVE-2026-103111 and `libssl3t64`/`openssl`
  CVE-2026-84782 - that Debian had fixed in `deb13u3` but the upstream image had not yet
  rebuilt for. Trivy (HIGH/CRITICAL, fixed-only) now reports 0 findings on the image (#76).
- **urllib3 2.7.0 → 2.8.0 and pyjwt 2.14.0 → 2.15.1** (transitive, via botocore/requests and
  databricks-sql-connector/mcp/snowflake-connector) for PYSEC-2026-4175/4176/4177 and
  PYSEC-2026-4140..4152/4183, published 2026-10-05 and later (#74).

### Changed

- **Tool declarations are now single-line `@mcp.tool(...)` directly above each `def`**,
  with `ToolAnnotations` in module constants and `as_tool_error` applied to the
  implementation functions instead of being stacked under the decorator. Done because the
  mcprush.com directory reads the tool surface statically from the repository and could not
  parse the previous multi-line/stacked form. `tools/list` from the running server is
  byte-identical before and after (names, descriptions, schemas, annotations) (#73).
- **Dependencies refreshed:** `mcp` 2.2.0 → 2.3.0, `databricks-sql-connector` 4.5.0 → 4.6.0,
  `databricks-sdk` 0.139.0 → 0.148.0, `snowflake-connector-python` 4.7.3 → 4.8.0,
  `google-cloud-bigquery` 3.45.0 → 3.46.1, `google-cloud-bigquery-reservation`
  1.27.0 → 1.28.0, `opentelemetry-sdk` 1.44.0 → 1.45.1 (#60, #75). Tool surface verified
  identical under `mcp` 2.3.0.

### Known, accepted

- `oauthlib` 3.3.1 stays flagged by pip-audit (PYSEC-2026-4114 / CVE-2026-49265, fix 4.0.0):
  `databricks-sql-connector` pins `oauthlib<4.0.0` through its current 4.6.0. The advisory
  is a PKCE `code_verifier` timing attack on the OAuth *authorization-server* side; this
  project is only an OAuth client (Databricks M2M via `databricks-sdk`) and never executes
  oauthlib. Accepted in `audit.yml` with a re-check date of 2026-12-01 (#77).
