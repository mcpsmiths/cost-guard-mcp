# v0.5.0 — 2026-10-15

The follow-up release to the 2026-10 security-audit remediation (0.4.0). Three PRs, each
verified by a runtime pass that drove the real server over stdio JSON-RPC against recording
fake warehouse SDKs and by the unit suite at 99% coverage: #106 stops the read-only tools from
waking a warehouse (`DECISIONS.md` #20), #107 makes both SQL tools accept read statements only
by default and closes the remaining query-path gaps the audit left open - the line-comment
scanner bypass, the unbounded BigQuery result polling and the serialiser-breaking nested
result cells (`DECISIONS.md` #13, #14, #15, #17) - and the registry-channel PR publishes the
MCP Registry listing from the tagged release instead of a personal host (`DECISIONS.md` #12
decided; the hosted release controls recorded under #10). Two entries are breaking; each is
marked on the entry and summarised first with its opt-out; the other caller-visible behaviour
changes follow at a glance. Every new environment variable is documented in `server.json`,
`.mcp.json.example` and the README.

### Breaking changes and opt-outs

- **Read statements only, by default.** `estimate_query_cost` and `run_query_bounded` refuse
  any statement whose first keyword (after comments and opening parentheses) is not `SELECT`,
  `WITH` (followed by `SELECT`/`VALUES`, at most 16 nested CTE levels), `VALUES`, `SHOW`,
  `DESCRIBE`, `DESC` or `EXPLAIN`, before any dry run or execution. Opt-out:
  `COST_GUARD_ALLOW_WRITE_STATEMENTS=1` (exactly that value). With
  `COST_GUARD_ALLOW_MULTI_STATEMENT_SQL=1` every statement must be a read, so BigQuery scripts
  that write now need both opt-outs. The authorisation boundary is still the deployed
  credential's grants - a read-only principal is the recommended configuration on all three
  engines; this gate is defence in depth (`DECISIONS.md` #13).
- **Read-only tools no longer wake a warehouse.** `check_credentials` and `estimate_query_cost`
  read the Databricks SQL warehouse's state first and, unless it is `RUNNING` (also when the
  state cannot be read), return `ok: false` / no byte or dollar figure without opening a
  session; on Snowflake the `CURRENT_REGION()`, `QUERY_HISTORY` and session-context reads run
  only when the pinned warehouse's `SHOW WAREHOUSES` state is `STARTED`, otherwise the estimate
  prices at Gen1 rates at the observed size with a caveat. Opt-ins:
  `COST_GUARD_DATABRICKS_ALLOW_WAREHOUSE_START=true` and
  `COST_GUARD_SNOWFLAKE_ALLOW_WAREHOUSE_RESUME=true` (exactly those values). Databricks
  principals without `CAN_VIEW`/`CAN_USE` on the warehouse are now refused by the read-only
  tools instead of being priced at the caller-asserted size. `run_query_bounded` is unchanged
  (`DECISIONS.md` #20).

### Other behaviour changes at a glance

- **`tools/list`:** `run_query_bounded`'s `outputSchema` gains the constant
  `rows_provenance: warehouse_data_untrusted` (additive); the `check_credentials`,
  `estimate_query_cost` and `run_query_bounded` descriptions changed (read-statement sentence,
  warehouse-state sentences). Names, input schemas and annotations are unchanged from 0.4.0.
- **Line comments end where the dialect's lexer ends them** (CR or LF on Databricks; LF on
  BigQuery and Snowflake, where a bare CR inside a comment is refused as ambiguous), and any of
  U+000B, U+000C, U+001C-U+001E, U+0085, U+2028, U+2029 inside a line comment, or a backslash
  before its terminator, is refused - closing the two-statement bypass the audit found
  (`DECISIONS.md` #15).
- **BigQuery result polling is bounded.** The RPCs inside `query_job.result()` carry the same
  30 s retry bound as every other BigQuery call; exhausted polling retries issue the bounded
  best-effort job cancel the 120 s watchdog does, instead of pinning a worker thread and an
  in-flight slot for ~10 minutes during a Google-side outage (`DECISIONS.md` #14).
- **Deeply nested result cells are capped** at 64 levels (`<nested value omitted: deeper than 64
  levels>` plus a `hint` naming the affected cell count - so `hint` can be set on an `ok`
  result; `status` remains the refusal discriminator) instead of tripping the MCP SDK's
  serialiser after a billed execution (`DECISIONS.md` #17).
- **Release process:** `release.yml` now publishes the MCP Registry listing
  `io.github.mcpsmiths/cost-guard-mcp` from the tagged commit after PyPI has the version,
  through the `mcp-registry` environment and GitHub OIDC with a pinned, SHA256-verified
  `mcp-publisher`; this is the first release whose listing is produced that way (the listing had
  been stale at 0.3.2). The `v*` tag ruleset, the environment deployment policies and the PyPI
  publisher binding are recorded in `DECISIONS.md` #10.

### Security

- **Breaking: read statements only by default.** `estimate_query_cost` and `run_query_bounded`
  refuse any statement whose first keyword is not `SELECT`, `WITH` (followed by `SELECT`/`VALUES`;
  CTEs nested more than 16 levels deep are refused too, so the walk stays bounded on
  model-controlled text), `VALUES`, `SHOW`, `DESCRIBE`, `DESC` or `EXPLAIN`, before any estimate or
  execution (`DECISIONS.md` #13; #93). Opt-out: `COST_GUARD_ALLOW_WRITE_STATEMENTS=1` (exactly). With
  `COST_GUARD_ALLOW_MULTI_STATEMENT_SQL=1` every statement must be a read, so BigQuery scripts now
  need both opt-outs. `run_query_bounded` results carry the constant
  `rows_provenance: warehouse_data_untrusted` (additive `outputSchema` change, the intended
  `tools/list` diff) and both tool descriptions changed. The authorisation boundary remains the
  deployed credential's grants (read-only recommended; SECURITY.md, README).
- **Read-only tools no longer wake a warehouse by default** (`check_credentials`,
  `estimate_query_cost`; `DECISIONS.md` #20; #91, #92). Databricks: the configured SQL
  warehouse's state is read through the Warehouses API first; unless it is `RUNNING` - also
  when the state cannot be read - `check_credentials` returns `ok: false` and
  `estimate_query_cost` returns no byte or dollar figure, with no session opened. Snowflake:
  `SELECT CURRENT_REGION()`, the `QUERY_HISTORY` read and `check_credentials`' session-context
  `SELECT` run only when the pinned warehouse's `SHOW WAREHOUSES` state is `STARTED` (skipped
  when no warehouse is pinned or the state cannot be read; the `QUERY_HISTORY` read is also
  skipped whenever `estimate_query_cost` gets no `warehouse` argument); the estimate then
  prices at Gen1 rates at the observed size with the byte-tier heuristic and a caveat, and
  `check_credentials` returns `ok: true` with a detail built from the `SHOW WAREHOUSES` row.
  `USE WAREHOUSE`, `EXPLAIN USING JSON`, `SHOW WAREHOUSES` and `SELECT CURRENT_WAREHOUSE()`
  still run. `run_query_bounded` is unchanged (its estimate and execution may wake the
  warehouse). Opt-ins to waking the warehouse: `COST_GUARD_DATABRICKS_ALLOW_WAREHOUSE_START=true`,
  `COST_GUARD_SNOWFLAKE_ALLOW_WAREHOUSE_RESUME=true` (exactly those values). Behaviour change for
  Databricks principals without `CAN_VIEW`/`CAN_USE` on the warehouse: the read-only tools now
  refuse instead of pricing at the caller-asserted size. Tool descriptions changed
  (description-only `tools/list` diff). The owner's per-statement attribution test is the
  recorded follow-up in `DECISIONS.md` #20.

### Fixed

- Single-statement scanner: a line comment followed by a quote, backtick, `$$` or `/*` right
  after U+000B, U+000C, U+001C, U+001D, U+001E, U+0085, U+2028 or U+2029 made the scanner end
  the comment early, open a construct the engine never sees and swallow the engine's top-level
  `;`, admitting two-statement text. Line comments now end where each dialect's lexer does (CR or
  LF on Databricks; LF on BigQuery and Snowflake, where a bare CR inside a comment is refused as
  ambiguous), and any of those eight code points inside a line comment, or a backslash before its
  terminator, is refused (`DECISIONS.md` #15; #104).
- BigQuery `run_query_bounded`: the result-polling RPCs inside `query_job.result()` inherited the
  library's 600 s default retry, so a Google-side outage that began after job submission pinned
  the worker thread and one in-flight slot for ~10 min instead of surfacing within the documented
  bound; they now carry the same 30 s retry bound as every other BigQuery call, and exhausted
  polling retries issue the same bounded best-effort job cancel the 120 s watchdog does
  (`DECISIONS.md` #14; #103).
- `run_query_bounded`: a result cell nested roughly 250 or more levels deep (BigQuery JSON,
  Snowflake OBJECT/ARRAY) tripped the MCP SDK's serialiser after the billed execution, so the
  host received a protocol error or `Error executing tool run_query_bounded` and the result was
  lost; nested values are now capped at 64 levels with the placeholder
  `<nested value omitted: deeper than 64 levels>` and a `hint` naming the affected cell count -
  `hint` can therefore be set on an `ok` result; `status` remains the refusal discriminator
  (`DECISIONS.md` #17; #105).
