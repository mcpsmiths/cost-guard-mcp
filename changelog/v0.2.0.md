# v0.2.0 — 2026-09-17

The published 0.1.1 package on PyPI never actually contained any of the work below — it
only existed in git history since 2026-09-13. This release ships all of it for the first
time, including a critical security fix that has been sitting unreleased since then.

### Added

- **Databricks engine**: `check_credentials`, `estimate_query_cost` (via `EXPLAIN COST`,
  tagged `HEURISTIC`), and `run_query_bounded`, with dual auth (PAT or OAuth
  machine-to-machine).
- **`check_credentials` tool** (all three engines) — pre-flight setup verification without
  running a real query.
- Snowflake/Databricks cost estimates now scale by a coarse byte-size tier instead of a
  flat 30-second runtime assumption — a 1 KB query and a 4 TB query no longer get an
  identical dollar estimate.
- Snowflake cost estimates are now calibrated from the caller's own recent query history
  (`INFORMATION_SCHEMA.QUERY_HISTORY`, no elevated privilege required) when an exact repeat
  of a query exists, falling back to the byte-size tier otherwise. Result-cache hits are
  deliberately excluded from the average.
- `warehouse_size`/`edition` parameters threaded through `estimate_query_cost` and
  `run_query_bounded` for Snowflake/Databricks.
- README onboarding quickstart.
- pre-commit.ci installed and verified (auto-fixes formatting/lockfile drift on PRs).

### Fixed

- **CRITICAL**: `redact_secrets` only redacted the first word of a multi-word secret (e.g.
  a `SNOWFLAKE_PASSWORD` containing spaces) — the rest leaked verbatim through `ToolError`.
  This was the exact class of leak the sanitization module exists to prevent.
- **HIGH**: `warehouse_size`/`edition` were unreachable from the public
  `estimate_query_cost`/`run_query_bounded` signatures — every Snowflake/Databricks dollar
  estimate silently assumed the smallest warehouse regardless of which one the query
  actually ran on, understating cost by up to ~512x on an X6LARGE warehouse.
- **HIGH**: Snowflake/Databricks `execute_bounded` didn't strip a trailing `;` before
  LIMIT-wrapping, causing a syntax error on LLM-generated SQL that commonly ends in one.
- Snowflake `_connect()` had no explicit login/network timeout and could hang indefinitely.
- Every tool-boundary exception (`SanitizedEngineError`, `ConfigError`, plain `ValueError`)
  was silently discarded by the `mcp` SDK instead of reaching the caller — replaced with a
  generic "Error executing tool X" with the real message withheld.
- Databricks `execute_bounded` used `dict(row)` to build result rows, which crashes against
  the connector's real row type (found via a live dry run against a production warehouse,
  not just unit tests).
- A BigQuery Reservations API failure during capacity-billing detection previously killed
  the entire cost estimate instead of degrading to a byte-only estimate.
- Neither engine explicitly closed its warehouse connection — a real resource leak,
  particularly for Snowflake, whose connector has no `__del__` fallback (unlike Databricks').
- `run_query_bounded` execution had no wall-clock cap and could hang indefinitely on a
  stuck warehouse or cold/suspended compute.

### Security

- Narrowed a bare `ValueError` catch in `as_tool_error` to a vetted `UserVisibleError`
  marker subclass, so an unaudited library `ValueError` can never be forwarded to a client.
- Enabled gitleaks secret scanning, Trivy container image scanning, and a `docker`
  Dependabot ecosystem.
- Dockerfile base image pinned by digest instead of a mutable tag.
- CI's `docker-build` smoke test now does a real MCP client round-trip (initialize,
  list_tools, call_tool) instead of grepping a substring from raw JSON-RPC output.
- `release.yml` now verifies the pushed tag matches `pyproject.toml`'s and `server.json`'s
  version before publishing, so a mismatch fails the release instead of silently shipping
  the wrong version.

### Known limitations

- Databricks warehouse-history cost calibration was investigated and found blocked: its
  Query History REST API redacts query text server-side, even for the caller's own queries.
- The underlying `mcp` SDK can drop an in-flight tool-call response if the client closes
  stdin before the tool finishes (tracked upstream:
  [modelcontextprotocol/python-sdk#2678](https://github.com/modelcontextprotocol/python-sdk/issues/2678)).
