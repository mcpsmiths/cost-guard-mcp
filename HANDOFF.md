# Cost-Guard MCP — Handoff Document

**Start here in a new session.** This doc contains everything decided so far — read it before writing any code.

## Mission

Build an MCP server that gives AI agents **pre-flight query cost & result-size guardrails** across data warehouses (BigQuery first, then Snowflake, Databricks deferred). Today, an agent using a warehouse MCP can silently trigger a very expensive full-table scan or flood its own context window with an unbounded result set — no warehouse MCP lets it learn "how much will this cost / how much data will this return" *before* running the query. This project closes that gap.

## ⚠️ THE CRITICAL SCOPING NUANCE — read before writing code

Fresh verification (2026-09-12) found that **Google's own `googleapis/mcp-toolbox` (16,373 stars, updated within the last day) has already shipped ~70% of the naive BigQuery-only pitch**: `dry_run` support (merged Aug 2025, PR #1057) and a `maximumBytesBilled` cap (merged ~March 2026, PR #2724). This is the single most popular DB-MCP project in the ecosystem — most users evaluating this space will already have it installed.

**The real, novel differentiation is NOT "a BigQuery dry-run wrapper."** It is:

1. **The dollar-cost translation layer** — turning bytes/credits/DBUs into an actual $ estimate an agent can reason about. mcp-toolbox exposes the raw dry-run byte count but does not do this.
2. **Snowflake and Databricks coverage** — genuinely uncovered by anyone at the *marketplace-discoverable* level, but inherently *approximate*, not precise, because neither vendor bills the way BigQuery does (see evidence below).

**Do not ship a v1 that's just BigQuery `dry_run` again** — it will read as redundant and pointless next to mcp-toolbox. Lead with the accuracy-tier-disclosed multi-engine dollar estimate as the headline feature from commit #1.

**UPDATE (2026-09-12 research refresh): the "Snowflake and Databricks coverage genuinely uncovered by anyone" claim is now known to be false at the code level, true only at the marketplace-discoverability level.** `SignalPilot-Labs/SignalPilot` already ships exactly this — a per-engine cost estimator spanning BigQuery/Snowflake/Databricks (plus 8 more engines) with session-budget enforcement — bundled inside a larger self-hosted "governed AI data agent" gateway (Postgres + Docker Compose + web UI), not a standalone MCP server. It has no formal, machine-readable accuracy-tier field (only an internal, unexposed "approximate"/"unknown" quality flag) and no per-call bound parameters (session-budget-only, not `max_bytes_billed`/`max_rows`/`max_estimated_cost_usd` per call). A second, closer analog — `exmergo/dex` — ships the identical estimate-then-confirm pattern for the same three engines as a Claude Code skill/CLI, not an MCP server at all.

**Revised differentiation for v1, now that both exist:**
1. **Zero-infrastructure standalone MCP server** — point any MCP client at it directly; no gateway, no database, no Docker Compose required (SignalPilot's biggest adoption friction).
2. **Formal, machine-readable accuracy-tier field** via `describe_engine_capabilities` — confirmed via independent research (both the competitive-landscape and MCP-protocol-tool-design angles) that **no shipped MCP server anywhere has precedent for this** — it is a genuinely novel contribution, not something to hedge on.
3. **True per-call bounds** on `run_query_bounded` (`max_bytes_billed`/`max_rows`/`max_estimated_cost_usd` as call parameters), fitting a single-shot autonomous agent tool call better than a session-level budget ledger.
4. **More defensible cost formulas** — SignalPilot's Snowflake/Databricks heuristics are flat, uncalibrated $/row constants; sourcing real credit-rate and DBU-rate tables (see "Snowflake mechanics" and "Databricks mechanics" below) is a real, achievable wedge.

Before finalizing the Snowflake/Databricks cost formulas, do a hands-on read of SignalPilot's `gateway/gateway/governance/cost_estimator.py` and `budget.py`, and Dex's connector implementation (`github.com/exmergo/dex`) — both are real, working prior art for exactly this problem.

## Key risk to manage

The two-thirds of the pitch that's actually novel (Snowflake + Databricks $ estimation) is also the least accurate and most support-burden-prone part. Risk: a v1 that either overpromises precision it can't deliver, or gets dismissed as "just EXPLAIN with extra math I could've done myself."

**Mitigation baked into the design as a hard requirement, not a footnote:** every response must disclose its accuracy tier — `PRECISE` (BigQuery), `UPPER_BOUND` (Snowflake), or `HEURISTIC` (Databricks, deferred) — so agents/users never over-trust a heuristic number. **Confirmed in the 2026-09-12 refresh: no shipped MCP server anywhere has precedent for this kind of tagging — it's a genuinely novel contribution, invest disproportionately in documenting it (tool descriptions, not just schema fields) since agents have no pre-trained expectation for it.**

## v1 tool list

1. **`describe_engine_capabilities(engine)`** — declares which cost signals are exact vs approximate per engine. Build this **first**; it bakes the "disclose accuracy honestly" contract in from commit #1. Set `readOnlyHint: true` in tool annotations (per current MCP spec 2026-07-28 — see below).
2. **`estimate_query_cost(engine: bigquery|snowflake|databricks, sql, warehouse?)`**
   - BigQuery → wraps `dryRun`, exact `totalBytesProcessed` → $/TiB, tagged `PRECISE`.
     - **Correction (2026-09-12 refresh)**: `referencedTables` is NOT on the `jobs.query` response (`QueryResponse`) — it only exists on `Job.statistics.query` (`JobStatistics2`), reachable only via the `jobs.insert`-dry-run-then-read-Job path. If lineage matters, use that path.
     - **Correction**: BigQuery itself exposes `totalBytesProcessedAccuracy` (`UNKNOWN`/`PRECISE`/`LOWER_BOUND`/`UPPER_BOUND`) on dry-run jobs — read and pass this through instead of hardcoding BigQuery as always `PRECISE` (queries touching external/federated/wildcard tables or tables with pending streaming buffers can return non-`PRECISE` values).
     - **New hard requirement**: BigQuery has two billing models — on-demand (bytes → $) and Editions/capacity (slot-hours → $, no fixed $/byte rate at all). Before emitting a $ figure, detect which model the project uses (check for an assigned Reservation); for capacity-billed projects, return bytes only with an explicit "capacity-billed — cost model does not apply" flag rather than silently misapplying $/TiB.
   - Snowflake → `EXPLAIN`-derived `bytesAssigned` upper bound → heuristic $ from warehouse size/credit-rate, tagged `UPPER_BOUND`.
     - **New requirement**: always `USE WAREHOUSE <target>` immediately before `EXPLAIN` and record the warehouse size/generation used — Snowflake's own docs confirm the plan "might differ depending on the size of the current warehouse" (defaults to XS assumptions if none is active), so `bytesAssigned` is not a pure function of SQL text alone.
     - **New requirement**: source credit-rate and $/credit tables from Snowflake's own dated Service Consumption Table (`snowflake.com/legal-files/CreditConsumptionTable.pdf`, re-fetch periodically — it's versioned/effective-dated), not hardcoded scraped numbers. Covers Gen1, Gen2 (non-flat-multiple rates, cloud-specific), Snowpark-optimized, and Interactive warehouse tiers.
     - **New disclosure requirement**: `describe_engine_capabilities` must state that the Snowflake estimate excludes Cortex AI Function ("AI Credits", billed by token count) cost — `EXPLAIN`'s `bytesAssigned` only reflects warehouse compute/scan, not AI-inference calls inside the SQL.
   - Databricks → `EXPLAIN COST`-derived Spark CBO row/byte estimate → heuristic $ from DBU rate, tagged `HEURISTIC` — **deferred past v1** (by choice/sequencing now, not by access blocker — see "Testing setup" below).
3. **`run_query_bounded(engine, sql, max_bytes_billed?, max_rows?, max_estimated_cost_usd?)`** — refuses/aborts if the pre-flight estimate exceeds the bound. Use native enforcement where available (BigQuery `maximumBytesBilled`), app-level cap otherwise.
   - **Refusal-signaling design (decided in the 2026-09-12 refresh)**: no shipped comparable MCP server (checked 3 BigQuery cost-guard servers found in the wild) actually uses `isError:true` for a cap-exceeded refusal, despite the MCP spec's own letter (SEP-1303) suggesting Tool Execution Errors should be `isError:true`. Do both: set `isError:true` **and** populate `structuredContent` with `{status: "refused", reason: "cost_cap_exceeded" | "row_cap_exceeded" | ..., estimate: {tier, value, ...}, hint: "..."}` — nothing in the spec forbids combining them, and it maximizes compatibility with clients that branch on either.
   - Set `readOnlyHint: true` if scope stays strictly bounded-read, but explicitly document in the tool description (not just the schema) that repeat calls still have a real monetary/quota side effect — the spec's `idempotentHint` has no vocabulary for "costs money each time," and clients must treat annotations as untrusted hints anyway.

## Build order (BigQuery-only slice first — 2-3 days)

1. `describe_engine_capabilities("bigquery")` — static capability disclosure
2. `estimate_query_cost("bigquery", sql)` — wrap `dryRun`, compute $/TiB, tag `PRECISE`. This is the core, most defensible, fastest-to-verify value.
3. `run_query_bounded("bigquery", sql, max_bytes_billed?, max_estimated_cost_usd?)` — layer `maximumBytesBilled` enforcement on top of step 2
4. Expand to Snowflake: `EXPLAIN`-derived estimate, tagged `UPPER_BOUND`
5. **Defer Databricks explicitly** — by choice/sequencing, not access uncertainty (Databricks Free Edition access is now confirmed viable — see "Testing setup" below). Flag as "deferred past v1" in the README rather than ship an unverified heuristic before the Snowflake slice is solid.

Realistic estimates: **2-3 days** for the BigQuery-only slice; **1-2 weeks** for the full BigQuery+Snowflake v1 (Snowflake auth setup, EXPLAIN-output parsing, and a credible byte→dollar heuristic each add real time beyond pure coding).

### CI pattern (decided in the 2026-09-12 refresh)

Mirror `googleapis/mcp-toolbox`'s own split, which runs **zero** live-cloud tests in GitHub Actions: fast, secret-free unit tests (dry-run cost math, response-schema parsing, tool-registration logic) run on every push/PR as a required check; a separate, clearly-isolated live-integration test tier (env-var-gated, hard-fails rather than skips if the var is unset — e.g. `BIGQUERY_PROJECT`/`SNOWFLAKE_ACCOUNT`) is excluded from the default test run and wired to `workflow_dispatch` + a scheduled job only, using GitHub **environment-scoped secrets with manual-approval protection** — never on `pull_request` from forks. Every live test creates uniquely-suffixed (UUID) temp resources with guaranteed teardown (`t.Cleanup`/`finally`).
- **BigQuery CI auth**: a single service-account JSON as a repo/environment secret is fine for now (move to Workload Identity Federation only if this leaves a personal/free-tier GCP project).
- **Snowflake CI auth**: **password auth is effectively dead for automation** — Snowflake's MFA-enforcement rollout has broken password-based CI/CD pipelines industry-wide. Use RSA key-pair auth (`ALTER USER ... SET RSA_PUBLIC_KEY=...`, store only the private key as a secret) or a Programmatic Access Token from day one.
- If live-account spend/rate-limits become a concern even against free tiers, add a VCR-style record/replay layer (`vcrpy` for Python) around each engine's HTTP layer — record once against the real dry-run/EXPLAIN response, replay in the fast PR tier, hit the live account only in the scheduled/nightly tier to catch API drift (the pattern `terraform-provider-google`/Magic Modules uses).

## Open decisions for the new session

- **Language/runtime** — ✅ **DECIDED in the 2026-09-12 refresh: Python**, on the official `mcp` SDK v2. Reasoning: the accuracy-tier contract (every response must carry a valid `PRECISE`/`UPPER_BOUND`/`HEURISTIC` field) is structurally harder to violate in Python, where a shared dataclass/`BaseModel` with that field as required is auto-validated on every tool return; Python's SDK derives the output schema from the return-type annotation, vs. TypeScript's manual `outputSchema` + hand-built `structuredContent` per handler. Python's warehouse-client ecosystem (BigQuery/Snowflake/Databricks) remains 10-25x more adopted by download volume. Both official SDKs are equally current (both went through a synchronous major v2 rewrite the same week, Jul 27-28 2026) — SDK maturity was not a deciding factor. **Known tradeoff, revisit if it matters**: all three official Python warehouse clients are confirmed synchronous/blocking (open, unresolved asyncio feature requests on all three) — every warehouse call needs `asyncio.to_thread` wrapping. This is a real correctness trap if forgotten and a genuine ceiling under high concurrent load, but a non-issue for this project's actual workload (one dry-run/EXPLAIN round-trip per tool call, local stdio, not high-fan-out). If this ever becomes a shared remote HTTP server fielding many concurrent calls, TypeScript's natively Promise-based warehouse clients would be the better-reasoned choice — revisit then.
- **Deployment model** — ✅ **DECIDED: local stdio**, user-supplied credentials via env vars. No new evidence from the refresh argues for remote HTTP; multi-cloud credential handling stays simpler this way.
- **Credential handling per engine** — ✅ **DECIDED**: env vars only, validated at startup with a clear engine-specific error, never accepted as tool-call parameters or committed to any file. BigQuery → `GOOGLE_APPLICATION_CREDENTIALS` (ADC), with optional service-account impersonation. Snowflake → `SNOWFLAKE_ACCOUNT`/`SNOWFLAKE_USER` + `SNOWFLAKE_PRIVATE_KEY_PATH` (key-pair, preferred) or `SNOWFLAKE_PASSWORD` (discouraged, log a startup warning) + **`SNOWFLAKE_ROLE` required with no default** (do NOT default to `ACCOUNTADMIN` — confirmed this is what Google's own official Snowflake sample does, and it's a concrete anti-pattern to avoid copying). Databricks → OAuth M2M (`DATABRICKS_CLIENT_ID`/`DATABRICKS_CLIENT_SECRET`) preferred, `DATABRICKS_TOKEN` (PAT) fallback with a "legacy, discouraged for production" startup log line. Non-negotiable P0 gate before shipping `estimate_query_cost`/`run_query_bounded`: wrap every warehouse client call (all three engines) in a handler that catches and re-raises a sanitized exception, and configure logging to redact secret-shaped fields before they reach any log sink — confirmed real precedent: `snowflake-connector-python` issue #1323 documents the connector embedding a plaintext password in exception objects, still unfixed at the library level. No OS-keychain integration or OAuth device flow for v1 — no comparable server in this space does either; would be scope creep against YAGNI.
- **Repo location** — no project existed yet in this workspace; this handoff doc is the first file in a fresh `cost-guard-mcp/` project root.
